# Locking — the lock file and the locking protocol

> Part of the [LibRed Jet / ACE file-format reference](README.md). This is a cross-cutting topic: it describes the **side file** ACE keeps beside a database and the byte-range locks taken on it, not a page type. The page-0 commit-slot table it works with is [page-00 §2.2](page-00-database.md#22-the-user-commit-byte-table-0xe00-0xfff).

Everything here is **measured** against ACE 16 (`Microsoft.ACE.OLEDB.16.0`, x64) over OLE DB, with a shared user, a second shared user, and exclusive and read-only opens. What was not measured is listed under [Not known](#not-known) and in `verification-backlog.md`. The lock layout is implemented as `JetLockLayout` (`LibRed.Core/IO`) and decoded by `tools/JetLockTrace`; both state the layout in code and are kept consistent with this file.

**What LibRed does.** On Windows every shared or read-only open — every connection, two in one process included — registers as a user of its own as §1 and §3 describe: its own handle on the lock file, its group-0 and group-1 bytes, its record (left unwritten when the file already holds exactly those bytes at its number); its close deregisters it and deletes the file when no other user is connected (the page-1 lock ACE takes at close aside). Its open is refused, with ACE's 3734 or 3733, while another user bars new connections (§3). So two connections of one process meet each other's locks exactly as two processes do, as ACE's do (§5). A writer writes **its own commit slot** around every batch of page writes in the order and with the values of §6 — slot `n` as shared user `n`, slot 0 holding the file exclusively, none when it is neither (off Windows, or when the lock file cannot be opened) — and a page-0 write never carries the slot table. A registered user reads the commit table at the start of each statement and of each commit, and when a slot has changed that no connection of its own process wrote, drops every cached page and re-reads the catalog (§6); the connections of one process share one page cache, so one reads another's commit on its next statement. A connection's design change of a table it has in use itself is refused at once, on every open, exclusive and off Windows included (§4). It takes **ACE's page write lock** on every existing page it writes, honours another user's, and runs a statement again when a page it got only after another user committed is not what it had read (§4). It takes **ACE's table locks** (regions 4–6) for every table a statement reads or writes and for every design change, honours another user's, and plans a statement again when it got a table only after another user committed (§4). An `INSERT` locks the table's TDEF page before anything else and reads its counters under the lock, and every change to the global maps locks page 1 before reading them (§4). Inside an explicit transaction it writes the pages a statement took out of the global free map and the AutoNumbers it drew, and lets page 1 and the table's TDEF page go, when the statement returns, as ACE does about 500 ms after it; its `COMMIT` locks the TDEF page again and adds its row and index counts to the page as the file has it then (§5). It reads a **chained long value** under its shared byte on the chain's first page, as ACE does, held for the statement, and its `UPDATE` replacing or `DELETE` removing one locks that page exclusively first, as ACE's do — refused with ACE's 3202, or, for a `DELETE`, leaving the chain where it is (§4). A query's **table locks are held by its result** until the rows have been read and the reader closed, as an open ACE reader holds them, and a table read through the Core API outside a statement is locked for each read or enumeration (§4). A child row's `INSERT`, and an `UPDATE` of its foreign key, finds the parent's key under ACE's **shared byte on the parent's index page** holding it, held to the end of the transaction, so another user's `DELETE` or `INSERT` of a parent row on that page is refused meanwhile, as ACE's are (§4). What is and is not covered is in §4 ([transactions design](../design/transactions.md)).

## 1. The lock file

A shared or read-only user locks a side file next to the database: **`<name>.laccdb`** for an `.accdb`. (Other extensions — the `.ldb` of an `.mdb` — are not measured.) **Every byte-range lock is on the lock file; none is on the database file.**

| | |
| --- | --- |
| Database file | opened read/write, share mode Read\|Write |
| Lock file | created if missing, read/write, share mode Read\|Write |
| Content | one **64-byte record per user**, at offset `(userNumber − 1) × 64`: computer name then security name, 32 bytes each. A user writes its record right after taking its user locks, in one 64-byte write, over whatever a dead user left there; records of other numbers are untouched |

**The record.** Each name is single-byte text **ended by a `00` and padded with spaces (`20`)** to 32 bytes. The computer name is the machine's name (on the measuring machine, `DESKTOP-D1RBTPV`, which is both its NetBIOS name and its host name, so which of the two ACE writes is not known); the security name is **`Admin`** for a database opened over OLE DB without a workgroup file (DAO writes `admin`, §3). A read-only user writes the same record. User 1 on machine `DESKTOP-D1RBTPV`:

```
00  44 45 53 4B 54 4F 50 2D 44 31 52 42 54 50 56 00   DESKTOP-D1RBTPV.
10  20 20 20 20 20 20 20 20 20 20 20 20 20 20 20 20
20  41 64 6D 69 6E 00 20 20 20 20 20 20 20 20 20 20   Admin.
30  20 20 20 20 20 20 20 20 20 20 20 20 20 20 20 20
```

These names are what an exclusive open refused by a connected user reports (§7). How a name longer than 31 bytes, or with characters outside ASCII, is written is not known.

An **exclusive** open (`Mode=Share Exclusive`) is different: the holder opens the database file with share mode None, **creates no lock file, takes no byte-range lock**, and writes commit slot 0 (`0xE00`).

### Lifecycle

- The lock file is created by the first shared user.
- A user that closes cleanly and finds no other user **deletes** it.
- A user killed without closing loses its locks with the process; the lock file stays. The next user reuses it, and the last clean closer deletes it.

## 2. Lock offsets

Every lock is an operating-system **exclusive** lock, taken **fail-immediately**. No OS-shared lock is ever taken; Jet's "shared" and "exclusive" are different byte ranges, not different lock modes. The locks lie far past the end of the lock file, so they are pure semaphores.

```
offset = (region << 28) | (page << 9) | byteInWindow
```

`(region << 28) | (page << 9)` is the page's **window**; byte 0 of a window is unused. The `<< 9` is not the page size.

| Region | Kind | Target |
| --- | --- | --- |
| `1` | User | not page-based: groups of 256 bytes — group 0 the users, group 1 the session bytes, group 5 connection control, group 6 tried when connection control refuses (§3) |
| `2` | Page write / read | data, index, long-value, usage-map and TDEF pages |
| `4` | Table read | the table's TDEF page |
| `5` | Table write | the table's TDEF page |
| `6` | Table deny-write | the table's TDEF page |

Region `3` is the white paper's Jet 2.x region; ACE 16 takes no lock in it.

**Shapes on a page window** (user number `n`):

- A **shared** lock is **one byte** at `window + n`.
- An **exclusive** lock starts at `window + 1` and is **`256 + n` bytes** long (257 for user 1, 258 for user 2): it covers every user's shared byte, and where it ends names the holder.
- An **upgrade** (measured for user 1 only): holding its own byte, the user locks `window + 2`, length 255.

## 3. User registration (region 1)

Region 1 is in 256-byte groups (`0x10000000 + group × 256 + byte`). User `n` holds, for its whole session:

- byte `0x10000000 + n` (group 0), and
- byte `0x10000100 + (n − 1)` (group 1).

**Connecting.** The user first tries `0x10000001`, length 255.

- *Alone*, that succeeds; the user releases it, takes `0x10000100` then `0x10000001`, and writes record 1.
- *With user 1 present*, the newcomer is refused on `0x10000001`/255, `0x10000100`/255, `0x10000100`/1 and `0x10000001`/1, then takes `0x10000101` and `0x10000002`, and writes record 2.

**Connection control (group 5).** Once it has its number and has written its record, every user tries the whole of group 5, `0x10000500`, length 256. Granted, it releases it and is connected.

A user `n` that bars new connections — `Jet OLEDB:Connection Control` set to 1 on its session ("passive shutdown") — locks and releases the whole of group 5, then locks byte `n` of it (`0x10000500 + n`; `0x10000501` for user 1) and holds it. Setting the property back to 2 releases the byte; closing the connection releases it, before the group-1 and group-0 bytes, so the bar never outlives the user that set it. A connected user's statements run as before while any user, itself included, holds a group-5 byte.

A newcomer refused the whole of group 5 (with user 1 connected, the newcomer user 2):

1. It locks and releases byte 0 of **group 6**, `0x10000600`.
2. It tries the group-5 byte of each other connected user — `0x10000501`; the newcomer's own (`0x10000502`) is not tried.
   - *Refused*: that user bars connections. The newcomer reads that user's record, releases its own group-1 byte and then its group-0 byte (its record is left as written), and the open fails with **3734** naming the record's security and computer names (§7).
   - *Granted*: released at once, and the newcomer starts again from the whole of group 5. A group-5 byte held by no connected user (`0x10000507` with users 1 and 2 only) is never tried, so it is never found.
3. After **10 rounds** in all, it releases its group-1 and group-0 bytes and the open fails with **3733**, an unknown user (§7). No round waits for the next: an open refused after ten rounds takes no longer than an ordinary open.

When byte 0 of group 6 is refused in step 1, the newcomer tries no group-5 byte. It tries the group-6 byte of every user number that has a record in the lock file — the file's length over 64 bytes — from the highest down to 1, its own number included, locking and releasing each one granted at once:

- *A byte of another user refused*: it stops there, reads that user's record, releases its group-1 and group-0 bytes and fails with **3734** naming that user. With three records in the file and the newcomer user 3, it tries `0x10000603`, `0x10000602`, `0x10000601`; with user 1's `0x10000601` held it fails with 3734 naming user 1.
- *Its own byte refused*: it names no one and ends the round, going back to the whole of group 5 for the next. Holding `0x10000600` and the newcomer's own byte (`0x10000603`) gives ten rounds of three tries (group 5 refused, `0x10000600` refused, `0x10000603` refused), then 3733. Holding `0x10000600` to `0x10000603` fails the same way: the own byte, tried first, ends each round.
- *None refused*: the next round. Ten rounds, then 3733, though a connected user holds its group-5 byte: user 1 holding `0x10000501`, or user 2 holding `0x10000502`, with `0x10000600` held from outside.

The walk covers the records, not only the connected users: a user 2 beside user 1, with a third record left in the file by a user that has closed, also tries `0x10000603` first.

Holding only group-6 user bytes, byte 0 free, changes nothing: the newcomer is granted byte 0, releases it, and goes on to the group-5 bytes as in step 2 (a refused `0x10000501` still gives 3734). Byte 0 of group 6 held alone bars nothing: group 5 is granted and group 6 never tried.

With byte 0 of group 6 granted, the first group-5 byte tried is that of user 1, `0x10000501`, even when the newcomer is user 3 and user 2 is connected too; it was refused in every such case, so the order beyond the first byte and whether the newcomer's own byte is tried are not measured.

**Setting connection control.** A user setting `Jet OLEDB:Connection Control` to 1 runs the same routine. With nobody barring, it locks and releases the whole of group 5, then locks and holds its own byte (`0x10000502` for user 2) and does not touch group 6. With another user already barring, it is refused the whole group, locks and releases byte 0 of group 6, tries that user's group-5 byte (`0x10000501`, not its own `0x10000502`), finds it refused, and stops: it takes and holds nothing and raises no error, and the property reads back 1. A second user's setting therefore bars nothing — only the first setter bars connections, and the bar ends when that user sets its own back to 2 or closes, a newcomer then connecting. With byte 0 of group 6 held from outside and a user barring, the setter walks group 6 as a newcomer does (all granted, as measured) and holds nothing. With a group-5 byte held by no connected user, the setter likewise holds nothing, and returns at once.

The property's value is the one last set, whatever is held: the second setter's reads 1 while it holds nothing, and setting it to 1 again once the first setter has let its bar go takes the setter's own byte. More of the property:

- It takes 1 and 2 only, and is 2 on a new connection; 0, 3 or −1 is refused with OLE DB's `DB_E_ERRORSOCCURRED` (`0x80040E21`, "Property value is invalid"), and the value stays as it was.
- Set to 1 again while the user holds its byte, it counts: the byte is held until the property has been set to 2 as many times, although it reads 2 after the first. Set to 1 three times, it takes three 2s, and a newcomer is refused 3734 until the third. A second setter's 1s while it holds nothing are not counted. Set to 2 while the user holds nothing, it does nothing.
- Closing lets the byte go however many times it was set.
- The user's statements and transactions do not touch it: the byte stays held across an `UPDATE`, a transaction and its rollback; set inside a transaction it takes or lets go of the byte at once, and the transaction's rollback or commit does not undo it.
- A read-only connection bars as a shared one does.
- An exclusive connection takes 1 and 2 and reads them back, with no error and no lock file: it holds nothing.

**What LibRed does with connection control.** Its connect tries the whole of group 5 and, refused, does what ACE's newcomer does above (`JetUserRegistration.Connect`), walking group 5 over the numbers below its own whose group-0 byte its search for a number was refused, ascending, and group 6 over the records in the lock file as above: it refuses the open with an `IOException` carrying ACE's 3734 or 3733 text, its group-1 and group-0 bytes released first; the open takes nothing else. It sets connection control through `JetDatabase.BarsNewConnections` — true for ACE's 1, false for 2 — by the same check (`JetUserRegistration.SetConnectionControl`): granted the whole group, it holds its own byte; refused, it holds nothing and raises nothing, the property reading true all the same; it counts repeated bars and lets the byte go before its group-1 and group-0 bytes at close, as ACE does above. Its group-5 walk is over the users its connect found connected below its own number; refused after a grant — another user's momentary try of its byte between the two — it runs the round again. An exclusive open, and a shared one off Windows or with no lock file, take the value and hold nothing. A process's connections make the check one at a time, connecting and setting alike, so one never finds another's momentary lock of the whole group covering that connection's group-5 byte and takes it for a bar; two processes doing it at once are not kept apart.

**User numbers.** User numbers 1 to 3 are measured. The next user to connect takes the lowest free number: a dead or closed user's number is reused and its record overwritten. The lock file grows by one record per number first used and is not shortened when a user closes.

**Each connection is a user.** Each OLE DB connection — in one process or several, read-only included — opens a handle of its own on the database and a handle of its own on the lock file, and takes a user number, a record and a commit slot of its own: three connections in one process hold the group-0 bytes of users 1, 2 and 3, on three lock-file handles, and each writes only its own slot. With OLE DB session pooling on (the default of `System.Data.OleDb`) a closed connection lets its handles and its number go the same. A connection does not read another connection's commit at once, in the same process either: it reads the committed row 3.8 to 5 s later (its refresh, §5), an autocommit `INSERT`'s as an explicit `COMMIT`'s. A table another connection creates is not found meanwhile (3078); a column another connection adds is read on the next statement.

**DAO in one process is one user.** Every DAO `Database` a process opens on the file — a second in the same workspace, one in a second workspace, one through a second `DBEngine` object (which is the same engine object) — belongs to one Jet user: one record in the lock file, one registration at the first `OpenDatabase`, and no lock-file call for the later opens. Its registration differs from an OLE DB connection's. Alone on the file, it tries `0x10000100`, length 255 (the whole of group 1), lets it go, takes `0x10000001` (its group-0 byte) and writes record 1 — it holds **no group-1 byte**; the security name in its record is `admin`, in lower case. Its close lets go of the group-0 byte and nothing else: no page-1 lock, no probe of the other users' bytes. (A DAO user registering beside another user, and an OLE DB user registering beside a DAO one, are not measured.) A second database opened in the same workspace shares the first's transaction: its `UPDATE` of a row the open transaction changed goes ahead, taking no lock. Between workspaces ACE arbitrates in memory, with no lock-file call and no retry: an `UPDATE` of a row another workspace's transaction, or its pessimistic recordset edit, holds is refused at once with **3188** (§7). The workspaces being one user, they hold one byte of a table's region-4 and region-5 windows between them: a statement of the second workspace refused 3188 let go of the table bytes the first workspace's open transaction held on the table, and the next statement of that transaction's workspace took them again.

**DAO recordsets.** A dynaset recordset takes the table's locks for writing at its open — the read byte, then the region-6 exclusive, the region-5 byte, the region-6 lock released — and holds the region-4 and region-5 bytes until it is closed. A pessimistic `Edit` (`LockEdits` true) takes the exclusive page write lock on the row's data page at the `Edit`, reading the page, and holds it until `Update` has written the page and the slot. An optimistic `Edit` takes nothing; its `Update` takes the page's exclusive lock, reads the page, and — the page having changed since the `Edit` — fails with **3197** and lets the lock go (§7). Measured in the default (page-level) locking mode only.

**What LibRed does with DAO users.** LibRed has no DAO surface: each of its connections registers as an OLE DB connection does. Beside a DAO user holding only its group-0 byte, its first try of the whole of group 0 is refused, its try of the whole of group 1 is granted and let go, and it takes the lowest number whose two bytes it can both take — the DAO user's number refused at its group-0 byte. What ACE's OLE DB connection does there is not measured.

**Exclusive opens in one process.** With a shared connection open, an exclusive open in the same process is refused with 3704, as from another process (§7). With an exclusive connection open — one database handle, no lock file — every other open in the same process, shared, read-only or exclusive, is refused with 3045.

**Closing.** The user locks page 1 exclusively (region 2); tries to lock every *other* user's group-0 byte (user 1: `0x10000002`, length 254; user 2: `0x10000001`, length 1 and `0x10000003`, length 253); releases; then releases its group-1 and group-0 bytes. Some `CREATE TABLE` / `DROP TABLE` statements make the same probe of the other users' bytes; which ones is not known.

## 4. Page and table locks

| Operation | Locks taken |
| --- | --- |
| Reading data or index pages | **none** — a `SELECT` reads a data page another user holds an exclusive lock on, and is not refused |
| Reading a long value | for a **chained** value, the user's shared byte in region 2 on the chain's **first page** only; none on its other pages, on the page of a value stored on a single page, or for a value stored in its row |
| `UPDATE` replacing a chained long value | additionally: an exclusive region-2 lock on the old chain's first page; none on the new chain's first page when it is appended |
| `DELETE` of a row with a chained long value | additionally: an exclusive region-2 lock on the chain's first page |
| `INSERT` of a child row; `UPDATE` of a child row's foreign key | additionally, after locking its own pages: the **parent** table's shared byte in region 4, then the user's **shared** byte in region 2 on the parent's index page holding the referenced key, then the region-4 byte released at once. The region-2 byte is held as the statement's page locks are (§5) |
| Opening a table for reading | shared byte in region 4 on the table's TDEF page (taken, released, taken again at statement start: a `SELECT`, `UPDATE` and `DELETE` open the table twice; an `INSERT` opens its table once, for writing) |
| A query's open reader | that shared byte, from the statement until the reader is closed — whether or not every row has been fetched, and inside a transaction too, where it goes at the close, not at `COMMIT`; a reader that is never closed holds it until it is finalized. A query read to its end at once (`ExecuteScalar`) lets it go at once |
| Opening a table for writing | additionally: exclusive lock in region 6 on the TDEF page, shared byte in region 5, then the region-6 lock released at once |
| Writing a page | exclusive lock in region 2 on that page — data, index, long-value, usage-map/global-map page 1 and TDEF pages alike |
| `ALTER TABLE`, `CREATE INDEX` | first an **exclusive region-4** lock on the table's TDEF page |
| `CREATE TABLE` | exclusive region-4 lock on the new table's TDEF page; `MSysComplexColumns` opened as a table for writing |
| `DROP TABLE` | exclusive region-4 lock on the dropped table's TDEF page |

`CREATE TABLE` and `DROP TABLE` also write-lock the catalog pages they change (the `MSysObjects` and `MSysACEs` TDEF pages, their index pages and data pages).

**Lock, read again, change.** After taking a page's exclusive write lock ACE reads that page from the file again before it changes it — page 1 (the global maps), a table's TDEF page, index pages and catalog data pages alike.

**An `INSERT`'s order.** After the table-open locks (regions 4, 6, 5 above), an `INSERT` takes the table's **TDEF page write lock first**, before any data, index or map page: it locks the TDEF page, reads it again, then locks the other pages it writes. The TDEF page is written on every `INSERT` (its counters). **Page 1** is write-locked only when the `INSERT` reserves a new run of pages — not on every `INSERT`, and more often when two users insert at once than when one inserts alone. Each user appends into a run of its own: two users inserting at once append into separate runs, with unwritten pages between them.

**Two users inserting into one table at once.** Every `INSERT` succeeds, and the AutoNumber values are distinct and contiguous. The only lock ever refused is the table's TDEF page write lock — page 1, index pages and data pages are not — so the TDEF lock serialises inserts into a table. A refused attempt is retried about 110 ms apart (§7). The holder lets the TDEF page go and takes it again within a millisecond for its next statement, so a waiting user can lose several rounds before it is granted. While both insert, the waiting user also tries the other user's group-0 user byte (§3) about twice per `INSERT` — once after letting its page locks go, once just after taking the TDEF lock — and is refused each time (what for is not known).

**A refused `INSERT`** — one refused a page another user holds, once the retries are spent — still writes the table's TDEF page and its own commit slot before it fails, so the AutoNumber it drew is not issued again.

**A rolled-back `INSERT`.** Begin, one `INSERT` into an AutoNumber table, `ROLLBACK`: the file is left as it was but for the table's AutoNumber counter (`0x14` on the TDEF page, the id drawn) and the user's commit slot, one higher — the same whether the `ROLLBACK` follows at once or two seconds after the `INSERT`. The row count, page 1 and the table's other pages are as before. LibRed leaves the same bytes.

**Another user's `CREATE INDEX`.** A user reading a table after another user's `CREATE INDEX` on it is refused with **3159** *"Not a valid bookmark."*: it takes its table-read byte, reads only the table's TDEF page again, and fails; it fails so until its periodic 5-second refresh. That holds between two ACE processes, so it is ACE's own behaviour, not a reaction to anything LibRed writes.

**Tables a transaction holds.** A table an explicit transaction has written — the target of its `UPDATE`, `INSERT` or `DELETE`, one that matched no row or changed nothing included — is held, its region-4 and region-5 bytes, until the outer transaction ends: after a statement on it that failed (a duplicate key, a null in a primary key), and after a nested transaction that wrote it was rolled back, another connection's `ALTER TABLE` is still refused with 3211. A table a statement only read is not held past the statement: the source of an `INSERT … SELECT`, and a `SELECT`'s table once its reader is closed, are another connection's to alter at once. A design change inside a transaction — `ALTER TABLE … ADD COLUMN`, one that failed (3380) included, `ADD CONSTRAINT … FOREIGN KEY` on both its tables, `CREATE TABLE … REFERENCES` on the referenced table — holds its exclusive region-4 lock until `COMMIT`: another connection's `ALTER TABLE` is refused with 3211, and its `SELECT`, `UPDATE`, `DELETE` and `INSERT` of the table with **3008** (§7). An `ALTER TABLE … ADD COLUMN` in an open transaction holds, besides the TDEF page's region-4 exclusive lock, the write lock on the catalog page it changed; at `COMMIT` it locks the TDEF page in region 2 for the write, and lets everything go. The other user's statements meanwhile try only their shared table-read byte on the TDEF page, and nothing else: a `SELECT`, `UPDATE` and `DELETE` 42 times (about 4.3 s), an `INSERT` 21 times (about 2.2 s), then 3008 — the statements that open the table twice two rounds, the one that opens it once one (above).

**Foreign keys.** A child row's check of its parent (the table above) pins the parent's **index page**, not the row. Another user's `DELETE` of any parent row whose key is on that page locks the parent's data page exclusively, is then refused the index page's exclusive lock — 21 attempts — lets the data page go and fails with **3218**; an `INSERT` of a parent row whose key goes on that page is refused with 3218 the same, and goes ahead once the child's transaction has ended. After the child's `COMMIT` the `DELETE` gets the index page, opens the child table for writing (its region-4, region-6 and region-5 locks), finds the related row and fails with **3200** (§7). Beside an autocommit child `INSERT` the `DELETE` waits for the child's deferred write (§5) and then fails the same. The other way round, a child `INSERT` beside another user's open transaction that has deleted a parent row whose key is on that page is refused its shared byte — whichever parent it references there — and fails with **3624** after about 2.2 s, one round of retries; once the `DELETE` has committed, a child of a parent left goes in.

**What LibRed does with foreign keys.** A registered user's child `INSERT`, and its `UPDATE` of a foreign-key column, find the parent's key through the parent's index (`StatementExecutor` → `Table.RowsWithKey` → `IndexTree.Seek`), and take the user's shared byte on the leaf page the key is found on before using the match (`PageChannel.LockPage`, the purpose `ReferencedKey`). The byte belongs to the transaction — an explicit one's to its `COMMIT` or `ROLLBACK`, a lone statement's to the statement's end — and is taken once per page in it; a rollback to a savepoint keeps it. Refused, it is retried 21 times and fails with ACE's 3624; one newly taken after another user's commit runs the statement again (up to three runs, then 3624), as a newly taken table lock does. The connection's own write of the page — its own parent row — goes ahead on top of the byte, as an upgrade (§2). The parent's region-4 byte is the one every table a statement reads takes, held for the statement where ACE lets it go after the lookup. So another user's `DELETE` or `INSERT` of a parent row on that page is refused by the page write lock above with 3218, and after the `COMMIT` the `DELETE` fails with ACE's 3200 text. A connection that is no Jet user — exclusive, unregistered, off Windows — takes no byte: there the transaction's commit checks the parent again instead, and refuses itself when another connection has deleted it. Measured against ACE 16: ACE's parent `DELETE` beside LibRed's child `INSERT` in a transaction fails with 3218 after about 2.2 s, and with 3200 after LibRed's `COMMIT`; LibRed's parent `DELETE` beside ACE's child `INSERT` in a transaction the same.

**A connection's own design change.** `ALTER TABLE`, `CREATE INDEX`, `DROP INDEX`, `DROP TABLE` and a DAO rename are refused **at once, with 3211 and no retries**, when the connection itself has the table in use — on an exclusive open as on a shared one, so it is not a lock that refuses it:

- a reader of its own is open on the table — nothing read yet, partly read, or read to its end — inside a transaction or not, until the reader is closed; the connection's own `INSERT`, `UPDATE` and `SELECT` of the table go ahead beside the reader, and so does a design change of another table;
- its open transaction has written the table in an earlier statement: after an `UPDATE` (one matching no row included), an `INSERT`, a `DELETE`, one that failed, and one made and rolled back in a nested transaction. A foreign key's referenced table counts: after an `INSERT` into the parent, `CREATE TABLE … REFERENCES` it and `ALTER TABLE … ADD CONSTRAINT … REFERENCES` it are refused, naming the parent.

It is not refused after a `SELECT` whose reader is closed, when the table was only the source of an `INSERT … SELECT`, after an autocommit write, on a table the transaction created, or once the transaction has itself changed the table's design — it then writes the table and changes its design again freely.

**Row-level locking mode** (`Jet OLEDB:Database Locking Mode=1` on both users) changes none of these shapes for SQL `UPDATE` / `INSERT`: the whole page is locked exclusively and another user's `UPDATE` of a different row on the same page is refused. (Recordset edits: not measured.)

**Long-value reads.** A user reading a chained value another user holds the chain's first page of exclusively is refused its shared byte and retries: let go after 1, 3 or 5 s, the read goes ahead within about 100 ms of it; held throughout, the column fails after about **6.5 s** over OLE DB with **3624** *"Could not read the record; currently locked by another user."* — a data reader's `Read()` returns the row after about 2.2 s, and fetching the memo column then fails after about 4.4 s more, the row's other columns still read. The attempts run about 108 ms apart without a break from first to last, the lock let go at any moment up to about 6.5 s being taken within about 110 ms: three rounds of the 21 attempts of §7, back to back, 63 in all. A read-only user takes the same shared byte, and is refused the same way. Another user's shared byte on the page stops no read.

**Long-value writes.** An `UPDATE` replacing a chained value, and a `DELETE` of a row holding one, lock the chain's first page exclusively, with the pages the statement writes, and let it go about 500 ms after the statement: with those pages after an autocommit statement; inside an explicit transaction too, where the data and usage-map pages it wrote are held to `COMMIT`. The new chain's first page, appended, is not locked. Against another user's shared byte on the first page, ACE's `UPDATE` replacing that chained value is refused after about 2.2 s with **3202** *"Could not save; currently locked by another user."*; its `UPDATE` of a value on a single page is refused with 3218, the page being one it writes; its `DELETE` of the row waits about 2.2 s and then deletes it, leaving the chain where it is: its pages stay taken in the global free map and owned in the column's long-value usage map, and their bytes are not touched — the file differs from that of the same `DELETE` unrefused in those two maps' bits alone.

**What LibRed does with long-value reads.** A registered user, read-only included, reads a chained long value under its shared byte on the chain's first page (`PageChannel.ReadLongValue`), and takes none for a value on a single page or in its row. Inside a statement — the outermost scope, in an explicit transaction too — the byte is held until the statement returns, and a byte newly taken after another user's slot has moved since the scope looked runs the statement again, as a newly taken table lock does (up to three runs, then 3624). Outside every scope — a query's rows read after it returned, a Core API read — it is held for the read alone, and a byte newly taken after another user's commit drops the cache first, so the chain is read as the file has it. A refused byte is retried as ACE retries it — 63 attempts, 100 ms apart, about 6.3 s — and then refused with ACE's 3624, for the whole row read rather than the long-value column alone. An `UPDATE` replacing a chained value, and a `DELETE` removing one (`PageChannel.LockPage`), lock the old chain's first page exclusively before reading the chain and giving it back, held for the statement and let go when it returns, inside an explicit transaction too — sooner than ACE's deferral of about 500 ms, as LibRed lets page 1 and the TDEF page go sooner (§5); through the Core API outside a statement, for that write alone — not to the end of its transaction, so another connection reading the value beside the open transaction reads the committed chain. Refused once the 21 attempts are spent, the `UPDATE` fails with ACE's 3202; the `DELETE` deletes the row and leaves the chain allocated and the column's, as ACE does: byte for byte the file ACE's refused `DELETE` leaves. Measured against ACE 16: LibRed's read of a chained memo just after ACE's `UPDATE` of it in an open transaction waits for ACE to let the old chain's first page go and reads the committed value; ACE's `UPDATE` of a chained memo LibRed is reading in a statement is refused with 3202, and goes ahead once the statement has returned; LibRed's `UPDATE` of a chained memo ACE has just read waits for ACE's read byte to go, and goes ahead.

**What LibRed does with page locks.** A registered user (§3) that is not read-only takes the exclusive region-2 lock above on every page it writes that is already in the file — data, index, long-value, usage-map, TDEF and page 0 alike (page 0 unmeasured: no ACE write of it was seen under a shared open) — and none on a page it appends. Inside a transaction the lock is taken when the page is first written, before its committed image is read as the commit's baseline, and held until the commit's batch has ended with its slot write, or until the transaction, or the savepoint frame that first wrote the page, is rolled back. Outside one it is taken and released within the one-page batch. Each connection is a user, with a lock-file handle of its own, so a page one connection of a process holds refuses another connection of the same process as it refuses another process: at the statement, after the retries, with 3218 — and no longer at `COMMIT`. The commit-time comparison of each page with the image it was derived from stays, as the check between connections that take no locks (off Windows, or with no lock file). A refused lock is retried as §7 describes, and then refused with ACE's 3218 text. A write that obtains a lock only after another user's slot has moved since its statement began may have been working on an image of the page older than the file: LibRed drops its cache and reads the page again, as ACE does; when it differs from the image the process held before (or that image cannot be known — below), it rolls the statement back and runs it again (up to three runs, then 3218) — through the SQL engine; a write made through the Core API is refused instead. Measured against ACE 16: each refuses the other's page with 3218, goes ahead once the other lets go, and neither loses the other's change on that page.

**What LibRed does with table locks.** A registered user takes the table locks of the table above on the table's TDEF page:

- every table a statement reads — every table it opens for its rows, not the catalog tables LibRed reads for itself — its shared byte in region 4, held for the statement and released when it returns, a writing statement's source tables included; every table it writes — an `UPDATE`'s and a `DELETE`'s target before a row is read, whether or not one is then written — that and, under a momentary exclusive lock in region 6, its shared byte in region 5, held inside a transaction until the outer `COMMIT` or `ROLLBACK`, through a failed statement and a nested transaction's rollback, as ACE holds them;
- a query's read bytes, inside a transaction or not, are handed to its result as the statement returns (`PageChannel.KeepStatementTableLocks`) and held until the enumeration reading its rows is disposed — an ADO reader's close — whether or not it has read them all, as ACE's open reader holds them. A result whose reading has not begun when the connection's next statement begins lets them go then (`ExecuteNonQuery` of a query keeps none), and closing the database lets every one go;
- a table read through the Core API outside a statement — a read, an index seek or a scan, in a transaction or not, and a query's rows read again after their result let go — takes its shared byte in region 4 for that read or enumeration alone, from its first row to its end or disposal (`Table.LockForRead`); a byte newly taken after another user's commit drops the cache, as there is no statement to run again;
- `ALTER TABLE` in every form, `CREATE INDEX`, `DROP INDEX` and `DROP TABLE`: region 4 exclusively, on the table they name (and on a foreign key's referenced table); `CREATE TABLE`: region 4 exclusively on the new table's TDEF page once allocated, and `MSysComplexColumns` opened for writing. Held as the read and write locks are: a lone statement's go when it returns, as ACE's DDL locks do; inside an explicit transaction they are held until `COMMIT` or `ROLLBACK`, as ACE holds them (above).

A read-only user takes the read locks only. A lock another user holds is retried as §7 describes, and then refused with ACE's 3211 naming the table; a refused read byte in region 4 — another user holding the table for a design change — is retried two rounds when the statement opens the table for reading and one when it opens it for writing, an `INSERT`'s target (`JetDatabase.OpenTable`'s `forWriting`), as ACE's are, and refused with ACE's 3008; a refused region-5 or region-6 lock, whose ACE errors are not measured, with 3211. A table lock taken only after another process's slot has moved since the statement's scope began means the table's design may have changed under the plan: the statement is rolled back, and bound, planned and run again on the re-read catalog (up to three runs, then 3211).

Each connection is a user: one connection's table locks refuse another connection of the same process as they refuse another process — its `ALTER TABLE` of a table the other's open result, or open transaction, holds is refused with 3211 after the retries. Within one connection the lock table counts its holders — its statement, its transaction, a result being read — and takes one OS lock per window. Since Windows refuses an exclusive range overlapping a byte the same handle holds, a region-4 exclusive lock is taken as ACE takes an upgrade — the connection's own shared byte, then the other users' bytes (bytes 1–256 of the window but its own; `window + 2`, 255 bytes for user 1, as measured; the shape for a higher user number is that rule carried on) — whether or not the connection held the byte before.

A connection's own design change of a table it has in use is refused at once with 3211, as ACE refuses it (above): while a result of its own is open on the table, and after its open transaction wrote the table in an earlier statement. This is kept by every connection, registered or not — an exclusive open, and one off Windows — from the same record of what its statements, transaction and results hold. A result that was never read does not count once the connection's next statement begins (LibRed cannot tell it from one dropped); an ADO reader counts from `ExecuteReader`. A read or enumeration made through the Core API outside a statement counts on a registered connection only. Of a transaction's table locks, none goes before the transaction ends.

Measured against ACE 16 with LibRed user 1: while ACE holds a table in a transaction (an `UPDATE` in it), LibRed's `ALTER TABLE … ADD COLUMN` and `CREATE INDEX` are refused, and fail with 3211 once LibRed's retries are spent; after ACE commits both succeed and ACE reads the new column on its next statement. LibRed holding a table in a transaction (an `UPDATE` in it) refuses ACE's `ALTER TABLE`, which fails with ACE's own 3211 after about 2.2 s; after LibRed commits it succeeds, and LibRed's next statement reads the new column. ACE reading a table in a loop while LibRed adds columns to it one statement at a time: no statement of either fails, and ACE reads each new column on the statement after it. A table LibRed creates appears to ACE within its 5-second refresh, not on its next statement (ACE gave 3078 meanwhile), as one another ACE user creates does (§6); one LibRed drops is gone on ACE's next statement (3011, *"could not find the object"*); one ACE creates or drops, on LibRed's next statement. After a LibRed `CREATE INDEX`, ACE refuses reads of that table with 3159 until its 5-second refresh, as it does after another ACE user's (above).

**What LibRed does with counters and allocation.** A registered user that is not read-only, inside a transaction (every SQL statement runs in one):

- **The TDEF page first.** An `INSERT` locks the table's TDEF page before it reads the counters it draws from and advances, and before it touches any other page of the row; so do a `DELETE`, a key-moving `UPDATE` and an emptying `DELETE`, before they read the counts they change. The lock is the page write lock above, taken ahead of the page's first write, and held as that is — to the end of the statement's transaction, or of the savepoint frame that took it — but in an explicit transaction it goes when the statement returns (below).
- **Page 1 before the maps are read.** Every change to the global maps — reserving a new run, giving pages back, the frees of a rollback, the merge of released pages at close, growing a map — locks the maps' holder page (page 1 where ACE creates them) before it reads them, through the allocator's one read of the maps. A page taken from the run the user already holds changes no map and takes no lock, as ACE's does not.
- **The maps written early in an explicit transaction.** A statement that succeeds inside an explicit transaction and has changed the maps only by taking pages — bits cleared, in place — writes those pages of the maps as a batch of its own as it returns, with the slot one higher, and lets them go (§5): the run it reserved is then taken for every other user, who can reserve a run of its own meanwhile. The next change to the maps in the transaction locks page 1 again and reads it as the file has it then. Maps the transaction has freed a page in, grown or converted are held to `COMMIT` as before; so are they after a statement that failed, until the transaction's next statement that succeeds. A rollback, of the transaction or to a savepoint, gives back the pages its undone writes had taken in such a write, in a batch of its own, and keeps the rest of the run reserved until close.
- **The TDEF page written early in an explicit transaction.** As a statement in an explicit transaction returns — one that failed included, once its own writes are undone — every TDEF page the transaction has changed only in its counters (row count, index counts, AutoNumbers) is written with the AutoNumbers it has drawn (`0x14`; and the complex id at `0x1C`, which ACE's early write is not measured with) and nothing else, in the batch with the maps above, and let go (§5). Its row and index counts stay with the transaction. Its next lock of the page — the next `INSERT`, `DELETE` or design change on the table — and its `COMMIT` read the page again under the lock and put the transaction's counting on top of it: each counter it changed as its change added to the file's value, an AutoNumber another user drew meanwhile kept. A rollback, of the transaction or to a savepoint, writes nothing of the AutoNumbers written early. A TDEF page the transaction changed in more than its counters (a design change), and a catalog table's (whose counts every rollback keeps), are held to `COMMIT`.
- **Read again under the lock.** A lock newly taken after another user's slot has moved drops every cached image, and the page is read again from the file. Only when it differs from the image the process held of it before the drop — what the statement may have read — is the statement run again (through the SQL engine; through the Core API it is refused); another user's commit that left the page alone does not stop it. Where that image cannot be known — a page evicted from the cache since the statement began, or a lock taken inside a read-only scope — the statement is run again, as it is for every newly taken table lock after another user's commit. The allocator's own reads made after taking the lock (a rollback's, the close's) are never refused: they read the page again and go on.
- **Appending.** A page this user takes past the end of the file is one the global map gave it, so no other user writes it. The pages below it that only keep the file contiguous are written as zeros only while they lie past the file's end: one another user has since written (into a run of its own) is left as that user wrote it. The file is grown, and a failed publication cut back, against its length as measured at that moment, never below a page another user has appended.

A refused `INSERT` keeps the AutoNumber it drew, as ACE's does: the statement's rollback writes it back onto the TDEF page, in a batch of its own ending with the slot, ahead of the batch with the counting the failure keeps (§6). (What else ACE's `INSERT` refused a locked page writes on that page is not measured; LibRed takes the row count back.)

LibRed does **not**: try the other user's group-0 byte while it waits; hold a long-value read lock for rows read after the statement returned beyond the read itself (what ACE's open reader holds of a chain is not measured); let go of a parent's table-read byte right after a foreign key's lookup (it holds it for the statement); defer letting go of a foreign key's byte on the parent's index page after an autocommit statement (about 500 ms in ACE); defer letting go of the old chain's first page as ACE does (about 500 ms); fail only the long-value column of a refused read. Each is listed in `verification-backlog.md`.

## 5. Lifetimes

| Case | When the locks are released |
| --- | --- |
| Autocommit `UPDATE` / `INSERT` | page locks when the pages are written — about **500 ms** after the statement returns, or at once if another statement follows immediately — and after the commit-slot write. Table bytes (regions 4/5) at statement end |
| Long-value read lock | about 500 ms after the statement, or at the connection's next statement — inside an explicit transaction too, not held to `COMMIT` |
| An `UPDATE`'s or `DELETE`'s lock on the old chain's first page | with the statement's page locks, about 500 ms after it, autocommit; about 500 ms after the statement inside an explicit transaction too, where the data and usage-map pages it wrote are held to `COMMIT` |
| A query's table-read byte | when its reader is closed — not before, though every row has been fetched; inside a transaction too, not held to `COMMIT` |
| A foreign key's shared byte on the parent's index page | with the statement's page locks: autocommit, when its deferred write goes out (about 500 ms after); in an explicit transaction, at `COMMIT` / `ROLLBACK`. The parent's table-read byte goes at once, inside the statement |
| DAO: a dynaset recordset's table bytes (regions 4/5); a pessimistic `Edit`'s page lock | at the recordset's `Close`; when its `Update` has written the page and the slot |
| Explicit transaction | data and index page locks and the table bytes (regions 4/5) of the tables it writes are **held until `COMMIT` / `ROLLBACK`**, and it is the data and index page locks that refuse another user's `INSERT` into the table meanwhile. Exception: an `INSERT`'s exclusive locks on the table's TDEF page and on page 1 are released about 500 ms after the `INSERT` — not at `COMMIT` — with those two pages written then (below); the TDEF page is locked again briefly at commit. A `DELETE`'s TDEF page is not held either: another user's `DELETE` beside it writes the page |
| DDL (`ALTER TABLE`, `CREATE INDEX`, `CREATE TABLE`, `DROP TABLE`) | every lock is released inside the statement |
| Idle | no locks are taken or refreshed |

**The early write inside an explicit transaction.** About 500 ms after an `INSERT` into an AutoNumber table inside an explicit transaction, while the transaction is still open, ACE writes one batch:

- the table's TDEF page, carrying **only the AutoNumber counter** (`0x14`, the id drawn) — the row count (`0x10`) and the index entry counts are not written until `COMMIT`;
- page 1, when the statement reserved a run (its bits cleared) or grew the free map's record — and not otherwise;
- its slot, one higher (`00 00` around a two-page batch, as §6).

No data, index, long-value or usage-map page is written early, and no page is appended. INSERTs about 2 s apart are written one batch each; three back to back are written in one batch, about 500 ms after the last, carrying the counter as the last left it. An `INSERT` that fails inside the transaction — a value too long for its column — writes the same about 500 ms after it: the TDEF page with the AutoNumber it drew, the page let go (another user's `INSERT` then draws the next). One that names its AutoNumber value and fails at the primary key writes that value as the counter, as ACE's explicit values set it (LibRed's do not lower it). A transaction that only `UPDATE`s writes nothing early; a `DELETE` writes no TDEF page early, nor holds it; a `DELETE` that reserved a run writes page 1 alone, about 500 ms after it, and the pages it frees are given back at close (page-05 §9.1).

`COMMIT` then writes one batch: the pages appended first, then the TDEF page's row count and index counts, the data, index and usage-map pages, and the slot. It writes the TDEF page as the file has it then: an AutoNumber another user drew meanwhile stays, and the transaction's row count change is **added** to the count the file then has — another user's `DELETE` beside the open transaction took a 400-row table's count to 399, and the `COMMIT` of the transaction's one `INSERT` made it 400, of its one `DELETE` 398. `ROLLBACK` writes nothing: the run stays taken in page 1 until close, when it is given back with the pages the undone writes took, and the file is left as it was but for the AutoNumbers drawn — the transaction's, and another user's meanwhile — and the slot (§4).

**Another user beside the open transaction** (a second ACE process, after the early write): its `INSERT` into the same table is refused with 3218 after about 2.2 s, having drawn the next AutoNumber, which its refused batch writes with the TDEF page and the run it reserved in page 1; its `DELETE` of a row elsewhere in the table is refused with 3218 too where the table has an index; on a table with no index, its `DELETE` of a row on a page the transaction has not written goes ahead, writing the TDEF page's row count, beside a transaction that has inserted a row or deleted one; its `UPDATE` of an unindexed column of a row on a page the transaction has not written goes ahead.

**Another connection in the same process** behaves as another process does. Two OLE DB connections, each in a transaction, inserting into one AutoNumber table with a unique index, the second straight after the first: the second's `INSERT` draws the id after the first's and is refused with 3218 after the retries — 2.2 s, or 2.7 s when the first's deferred write falls inside them; the first commits; the second, rolled back or committed with nothing, draws the next id again. An autocommit `INSERT` beside the open transaction is refused the same. Two transactions updating different rows of one data page, moving keys in one index leaf, or updating one row: the second's `UPDATE` is refused with 3218 after about 2.2 s, and goes ahead once the first has committed; updating rows on different pages of a table, an unindexed column, both go ahead and both commit. A page a nested transaction wrote and rolled back is let go at that rollback — another connection's `UPDATE` of it goes ahead — while a page the outer transaction wrote stays held. Two transactions each creating a table: the second's `CREATE TABLE` is refused with 3218. Another connection's `DELETE` of a parent row whose child the open transaction inserted is refused with 3218 after about 2.2 s, by the child's shared byte on the parent's index page (§4). Two connections writing in turn with no transaction wait for each other's deferred write, about 540 ms, and go ahead.

While one connection waits out its retries, a `COMMIT` of the holding connection issued from another thread does not run: it returns only when the waiting statement has failed, about 2.2 s after it began. The waiting statement does not go ahead on it.

**What LibRed does.** It writes what a statement took of the global maps and the AutoNumbers it drew, and lets page 1 and the TDEF page go, as the statement returns — sooner than ACE's deferral, as its autocommit write already is; a statement that failed writes its AutoNumbers so, not the maps (§4). Its `COMMIT` and its next lock of the TDEF page put its counting on top of the page as the file has it then, as ACE's `COMMIT` does. A `ROLLBACK` writes the pages its undone writes took back into the free map at once, where ACE leaves them taken until close; the file ends the same after close. Its connections in one process are users of their own, as ACE's are: a second connection's `INSERT` draws the id after the first's and is refused at the statement with 3218 after the retries, and the other cases above end as ACE's do. A statement waiting out its retries holds the process's publish gate (§7), so the holding connection's `COMMIT` on another thread waits for it to fail, as ACE's does. A connection reads another's commit on its next statement, through the page cache the process's connections share, where ACE's reads it at its refresh. A foreign key's byte on the parent's index page goes with the transaction's page locks — at the statement's end on its own, where ACE's goes with its deferred write.

**Idle poll.** Each shared user reads the whole 512-byte commit table at `0xE00` every **5 seconds**.

**A deferral held to the next statement.** An autocommit `UPDATE` that ACE starts within milliseconds of another user's commit (no ACE statement between) keeps its page lock, and its write, while the connection is idle — still held 3 s later — and lets go when the connection runs its next statement, a `SELECT` included. With an ACE statement between the other user's commit and the `UPDATE`, or a second's pause, the lock goes about 500 ms after the `UPDATE` as above. Nothing is lost either way: both users then read both changes.

**A kill inside the deferral.** A user killed right after an autocommit `UPDATE` returned (inside the ~500 ms) had written nothing: the update is lost, the file is not left suspect, and later opens succeed.

## 6. Commit slots and page writes

A user writes only **its own** 2-byte slot ([page-00 §2.2](page-00-database.md#22-the-user-commit-byte-table-0xe00-0xfff)): `0xE00 + 2n` when shared, `0xE00` when exclusive. For each batch of page writes:

- **One existing page:** the page, then the slot (counter + 1). `00 00` never appears.
- **Two or more existing pages:** the slot (`00 00`), the pages, the slot (counter + 1). The slot reads `00 00` for exactly as long as the pages are being written — the white paper's "mid-write to disk" state.
- **Pages newly appended to the file** are written first — a 1-byte write at the last byte of the new page, then the full page(s) — before the leading slot write (`00 00`).
- Every batch **ends with a slot write** storing the user's commit counter plus one (little-endian 16-bit); the page locks are released after it. This holds for a lone statement, an explicit transaction's commit and closing the connection (a one-page batch: counter + 1 only).
- The counter rises by exactly one per batch; the other users' slots and slot 0 are untouched.

**A failed autocommit statement** (measured, ACE 16 user 1, on files LibRed built; the slot read at the statement's return, about 2 s later and after close):

| Statement | Batches | What they write |
| --- | --- | --- |
| Single-row `UPDATE` refused at a unique index | none | — |
| Multi-row `UPDATE` refused at a unique index on its second row, no page allocated | one, after the statement returned (nothing at return) | the table's index and data pages, carrying bytes of the undone change (the refused key on the index page) |
| Multi-row `UPDATE` refused because a text value is too long | one, after the statement returned | the table's data page, carrying bytes of the undone row |
| Multi-row `UPDATE` that allocated pages (a 24,000-character memo; 899 index keys lengthened) and then failed — at a unique index, or at a `CHECK` | one after the statement returned, one at close | the first: page 1 (the run it reserved, bits clear), the table's pages, and the pages it appended, which stay in the file; the second: page 1, the run given back |
| `INSERT` into an AutoNumber table refused at a unique index | two: one before the statement returned, one after | the TDEF page: the first with the AutoNumber drawn (`0x14`), the second adding an index count (`0x43` on that table) |
| `INSERT` into an AutoNumber table refused by a `CHECK` | one, before the statement returned | the TDEF page, the AutoNumber drawn (`0x14`) |

A control session (open, `SELECT`, close) writes nothing.

**A `ROLLBACK` of an explicit transaction that reserved a run** (1,290 `INSERT`s; or a 24,000-character memo `UPDATE` and a 28,000-character `INSERT`): one batch inside the transaction, writing page 1 with the run reserved (about 500 ms after the statement that reserved it, §5), none at the `ROLLBACK`, and one at close, page 1 with the run given back. Every page ends as before the session, the slot two higher. LibRed writes page 1 with the run reserved as that statement returns, a batch at the `ROLLBACK` giving back the pages the undone writes took (the rest of the run kept, its bits clear), and the same one as ACE at close: the same bytes at the end.

**The exclusive holder's slot 0** can only be read before and after a session, since nobody else can open the file meanwhile. It is a little-endian counter like the others: from `01 01` (257) on the Northwind fixture, an exclusive open closed at once leaves it at 257, a `SELECT` leaves it, one `INSERT` raises it by one, and `CREATE TABLE` followed by three `INSERT`s raises it by five; slot 1 is untouched throughout. Which writes in the five-batch session are the extra batch, and the slot's value during a batch, are not known.

**Another user's commit.** With LibRed (user 1) and ACE (user 2) in one file and their writes taking turns, each reads the other's rows: ACE within its page refresh (under 7 s), and LibRed on its first statement after ACE's slot moves. ACE's slot rose by exactly its number of `INSERT`s, each landed before LibRed read it, and by nothing at close. A file LibRed has written its slot in opens, reads and writes in ACE.

**What LibRed does with the slot.** A batch is one publication: a transaction's commit, or a page write outside a transaction. Appended pages are written first (the file grown by `SetLength` when the page lies past its end, not by ACE's 1-byte write); then, with two or more existing pages, the slot (`00 00`); the existing pages; and the slot (counter + 1). The counter is the slot as the file holds it, read through the page cache, whose page-0 image every slot write updates. The slot is a 2-byte write at its own offset, handed to the OS at once. Page 0 itself is written only up to `0xE00`, and its cached image takes the table back from the file, so a page-0 write — a format-version raise, a password change — leaves every other user's slot as it is on disk. The commit-time conflict check ignores a difference confined to the table. If a publication fails part-way and every page written is put back, the slot is put back to its value before the batch; if a page cannot be put back, the slot is left as the batch left it (`00 00` after two or more existing pages). A page the batch would leave as committed is not written, and a batch left with none writes nothing, the slot included; a write outside a transaction that changes nothing takes no page lock.

**A failed statement (LibRed)** puts every page back exactly, so it writes only what the rollback must keep, gathered into at most two batches: the AutoNumbers drawn, then the global maps put right (the run reserved kept, its bits clear, the pages the undone writes took from it freed) and the counting a failure keeps. Its slot moves as ACE's does in each case of the table above, but for the two where ACE's one batch carries only bytes of the undone change: LibRed writes nothing there. The batch it writes goes out when the statement fails, not deferred.

**Noticing another user's commit (ACE).** A user reads the 512-byte commit table on its 5-second poll (§5), and not at the start of a statement: no statement reads it. Each user's poll runs from its own connect: two users connected a few seconds apart each poll every 5 seconds, offset by that gap. Between another user's commit and the reader's next poll, its statements run on what it has cached — a statement on a table it has read reads only the table's TDEF page, which every statement reads again under its table-read byte whatever the slots say, and none of the table's other pages; one naming a table created meanwhile does no file I/O at all and fails with 3078. After a poll that saw a slot move, the next statement reads the catalog pages again (the `MSysObjects` pages among them) and every page of the tables it uses. A `CREATE TABLE` and a `DROP TABLE` write their batch, and their slot, inside the statement; an autocommit `UPDATE` writes its with the deferred write (§5).

**Noticing another user's commit (LibRed).** Unlike ACE, LibRed looks at the start of every statement, which its locks rely on (a lock newly taken after another user's commit runs the statement again). A registered user reads the 512-byte table at the start of each outermost statement scope and each commit — one positional read on a handle the process's connections share, no allocation — and compares it with the table as last seen, in which every slot write of the process's own connections is noted as it is made: they publish through the one page cache, so only another process's slot can differ. On a change it drops every cached page image and parse, measures the file's length again and marks the schema changed, so the catalog and the format version are re-read. An open transaction keeps its own pages; its commit then compares them with the file and refuses on a page another user changed. A page another user changes without moving its slot stays cached and is served stale. An exclusive or unregistered channel does not look.

## 7. Conflicts and errors

A refused lock is retried: **21 attempts in all, about 108 ms apart (~2.2 s)**, then the statement fails. A user that lets a lock go and takes it again for its next statement within a millisecond can win every round against such retries (§4). A refused long-value read is retried three such rounds back to back, 63 attempts (§4). LibRed retries a refused page write lock, long-value lock, referenced-key lock or table lock the same way — 21 attempts, 63 for a long-value read, 42 for the read byte of a table opened for reading, sleeping 100 ms between them — holding its statement's publish gate meanwhile, so the process's other statements on the file wait with it (only its writers, when the waiting statement only reads), the holder's `COMMIT` among them when the holder is a connection of the same process, as ACE's waits (§5); it does not try the holder's user byte.

## Not known

Unmeasured, and so not stated as fact above:

- The slot of an exclusive holder (slot 0), and of a second concurrent user, during a multi-page batch; the `01 00` cases beyond those in page-00 §2.2. LibRed's exclusive holder writes slot 0 by the shared rule.
- What group 6 of region 1 is for, and what holds its byte 0 or its per-user bytes in ACE; whether group 1 means anything beyond being the session byte.
- Connection control: what else holds group 5 (a compact or repair, an exclusive open's attempt, Access's own UI); the order in which a newcomer tries the group-5 bytes beyond the first (user 1's) with several users barring, whether it tries its own, and whether the walk covers the records or only the connected users (LibRed walks those its search was refused below its own, ascending); a read-only newcomer; a newcomer's refusal by a bar set by a user other than user 1 with byte 0 of group 6 free. A setter's lock calls beyond the two cases traced in §3: whether a repeated 1 runs the check again or only counts, how many rounds it makes when it finds no holder, which group-5 bytes it tries when it is not the highest connected user, and what it does when its own byte is refused just after the whole group was granted.
- User numbers above 3 and the bound of 255, and what an open beyond it meets; lock-file names for extensions other than `.accdb`.
- DAO: how a DAO user registers beside another user, and how an OLE DB user registers beside a DAO user holding no group-1 byte; DAO between processes; row-level locking for recordset edits (DAO / ADO cursors); DAO deny-read / deny-write table opens; snapshot and table-type recordsets.
- A kill landing between the leading and closing slot writes of a multi-page batch: the slot then holds `00 00`; what the next open does is not known.
- What ACE stores after `FF FF`. LibRed goes on from `00 01` (256, a fresh file's value), never into `00 00` or `01 00`, and counts on from `00 01` when its own slot holds either of those.
- What a reader does on finding another user's slot at `00 00` — mid-batch. LibRed does not wait: it drops its cache and reads, and reads again once the slot moves on.
- What ACE compares in its 5-second read.
- What ACE does when page 1's write lock itself is refused (assumed: the same retries, then 3218 — LibRed does that); concurrent `DELETE`s that free pages; an `UPDATE` that moves a row to a new page; long-value page allocation under contention; index page splits and DDL that allocates, beside another user's `INSERT`; the close-time release of held pages (page-05 §9.1) with another user connected — LibRed's close merges every bit of the global released-pages map then, as ACE's close does alone.
- Whether ACE locks page 1 when it changes a reference-form global map's bitmap page.
- What the waiting user's tries of the other user's group-0 byte during concurrent `INSERT`s (§4) are for.
- Inside an explicit transaction: whether the early write's ~500 ms runs from the first statement of a burst or the last; whether `COMMIT` adds the index counts to the page as the file has it as it adds the row count (no other user's statement that changed an index count succeeded beside the open transaction); which lock refuses another user's `DELETE` elsewhere in a table with an index; what a failed statement other than an `INSERT` writes early, and whether a failed one writes page 1 early; whether a statement that frees pages in the free map (rather than releasing them) writes page 1 early; whether a key-moving `UPDATE` holds the TDEF page; the complex id (`0x1C`) in the early write.
- Foreign keys: what a child `INSERT` that finds no parent locks; whether a statement that fails after its check, or a rollback to a savepoint, lets the parent's index-page byte go; whether an `UPDATE` of a child row's other columns, or of one of two foreign keys, takes the byte for the foreign keys it left alone (LibRed checks, and locks, every foreign key of the row once one of them changes); a cascading `UPDATE` or `DELETE`.
- Long-value reads: whether a statement reading one chain twice takes its byte once; whether an open reader holds the byte of a chain it has read; what an `UPDATE` replacing a chained value does with its other pages, and what an `UPDATE` refused 3202 leaves; what LibRed's read meets when a `DELETE` or `UPDATE` of ACE's has freed the chain and the pages have been reused; what a `DELETE` with no `WHERE` locks of the chains it frees.
- What ACE does to a page lock it is refused partway through a statement that already holds others — whether it lets those go before retrying.
- Why the deferral above is held to the next statement, and for how long an idle connection would hold it.
- Table locks: what a user's region-6 exclusive attempt does when it collides with another user's momentary one or a DAO deny-write holder; what ACE reports when its shared byte in region 5 is refused; the locks of `DROP INDEX`, of `ALTER TABLE` beyond its first lock and of `DROP TABLE` beyond its first; table locks under DAO deny-read / deny-write opens and for a read-only user; what a reader left open across `COMMIT` holds; whether a failed design change other than `ADD COLUMN` keeps its lock to `COMMIT`; which other statements probe the other users' bytes.
